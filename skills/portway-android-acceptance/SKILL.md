# Portway: приёмка Android

Подготовь исполнимый протокол, помоги владельцу провести его и фиксируй только наблюдённые результаты. Подготовленный сценарий не является пройденным испытанием.

## Источники и подготовка

Найди рабочий корень Portway по README, DOC-061 и OpenAPI; пути `docs/...` здесь относятся к нему. Прочитай текущий status/plan, `docs/52-build-deploy-and-operations.md`, нужные TC и § 7 формы протокола в `docs/57-verification-and-traceability.md`, связанные критерии DOC-014 и состояния DOC-061.

Сверь APK/revision/config и доступность нужного реального endpoint с OpenAPI и кодом. Определи модель телефона, Android/API level, Google Play Services, permission, сеть и installation. Android 16 — целевой контекст проекта; актуальные SDK/API-особенности проверяй по официальной документации при необходимости. Не меняй требования под доступный стенд.

Уточняй только недостающие условия, влияющие на прогон. Если телефона/FCM/стенда нет, подготовь протокол по [сценариям](references/device-scenarios.md) и [форме evidence](references/evidence-template.md); реальную часть оставь `NOT_RUN` или `BLOCKED` с причиной. ADB доступ и запуск реального опасного/платного действия не следуют автоматически из вызова skill.

## Выполнение

- Указывай для каждого действия, что делает владелец, что создаёт тестовый backend и что наблюдает исполнитель. Используй безопасные контролируемые fixtures на сервере только там, где это допускает конкретный TC; не подменяй реальную доставку FCM локальным уведомлением.
- Для push различай foreground, background, normal terminated и force-stop через настройки. Критерий и число trials бери из актуального TC-012/ПМИ; отказ permission и края — TC-032. Accepted провайдером не доказывает delivered/tapped на телефоне.
- Для апрува наблюдай server deadline, reauth/GET latest, stale/expired/revoked состояния, отсутствие двойного решения и разницу server ACK/tool outcome. Проверка с телефона не разрешает выполнять произвольную shell-команду.
- Для SSE разделяй проверку reconnect/gap/410 и количественную задержку: p95 проверяется по выборкам и коррекции часов из DOC-057, а не секундомером одного события.
- Для ZIP проверяй системный SAF/picker, scoped доступ, отмену и сетевые сбои, preview/mapping/unresolved. Для переноса на второй host/model не называй эмуляцию реальным переносом.
- Для доступности проверяй действия и чтение полных аргументов с TalkBack, большим шрифтом, клавиатурой, поворотом и обеими темами. Скриншот красивого экрана не подтверждает focus order или touch target.

## Evidence и завершение

Сохраняй исходные измерения, фактические шаги, revision/config, условия, expected/actual, дефект/ограничения и безопасные ссылки на артефакты. Не записывай credentials, токены и полные чувствительные payload; идентификаторы и скриншоты редактируй по необходимости, сохраняя пригодность проверки.

Если сценарий не выполнен полностью, не повышай весь TC до PASS. Сохрани исходный FAIL и отдельно результат повторного прогона; после изменения значимой revision/config явно обозначь необходимость повторной проверки. Обнови DOC-057 и связанные BL/status/plan в пределах фактически полученного evidence.

Отчёт должен различать: протокол подготовлен; подмножество проверено локально; реальный прогон на устройстве завершён; приёмка владельцем подтверждена. Не заявляй владельческое подтверждение без него.
