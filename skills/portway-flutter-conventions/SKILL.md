# Portway: Flutter-клиент

Работай в границах текущей клиентской задачи и подтверждённого плана. Тексты общения/документов — русские, код/имена файлов — английские, строки UI — русские через ARB/l10n. Не запускай всю программу разработки при вызове навыка для отдельного исправления.

## Источники перед реализацией

Пути отсчитываются от рабочего корня Portway (`README.md`, `docs/61-android-screens-flows-and-api.md`, `api/openapi.json`), не от папки skill. Прочитай актуальные `docs/implementation-status.md`, `docs/implementation-plan.md`, нужные UI и состояния DOC-061, требования SRS и профильные документы из [карты контрактов](references/client-contracts.md).

Требования и решения владельца не выводятся из наличия endpoint. Сверяй DOC-036, OpenAPI и код; расхождение фиксируй явно. Нереализованный endpoint скрывается за заменяемым repository fake/real, а fixture-режим и его результаты видимо помечаются. Успешный fake не становится реальным ответом сервера.

Сохраняй выбранные в DOC-020 библиотеки/архитектуру. Если решения ещё нет, выбери и обоснуй подход для состояния, навигации и DI там и в DOC-061; не принимай название из примера за обязательную зависимость. Перед выбором SDK/API проверь текущую официальную документацию Flutter/Android/пакета; не закрепляй «актуальный» targetSdk из памяти.

## Если клиента ещё нет

При создании навыка владелец подтвердил: Flutter-клиент не реализован, есть дизайн Portway в Figma. При каждом новом задании проверяй фактическое наличие `pubspec.yaml`, Dart-кода и тестов; это исходный контекст, не вечный статус проекта. Доступный Flutter SDK, UI-макеты и контракты сами по себе не являются приложением.

Для первой реализации начни с согласованного среза: решения архитектуры, структура Flutter-пакета, ARB/l10n, навигация и repository boundary с явными состояниями. Создание приложения разрешается задачей владельца, а не самим чтением skill. Если заказан только план/аудит, подготовь его без генерации клиентского кода. Существующий этап 0 и его gate сохраняй, когда владелец заказал полный workflow и ещё не подтвердил следующий этап.

Дизайн читай из нужного Figma-файла доступными инструментами с их обязательными prerequisites; API/состояния бери из документов. При недоступном файле фиксируй непроверенную визуальную часть, не выдавай бриф или Comet за текущие экраны Portway.

## Границы клиента

- Слои и session coordinator бери из DOC-020 `#flutter-architecture`: widget не источник серверных прав, deadline и состояния запуска. При смене установки не смешивай auth, потоки, кеши и pending destination разных хостов.
- Для каждой мутации определяй её протокол по DOC-036, включая исключения auth. Потерянный ответ, повтор логической операции и новая операция — разные случаи; не выдавай новый key вслепую. Версионируемые изменения сверяй с правилами `If-Match`.
- Никаких server credentials в APK. Проверь жизненный цикл session/device proof и временных значений формы: storage, логирование, восстановление состояния, dispose/logout. Доступ к реальному API требует разрешённого контекста; skill не разрешает сам начать платные запуски.
- Состояния auth, SSE, апрува, push и пакетов реализуй по профильным разделам. Особое внимание — неизвестному исходу и возврату из фона; визуальная анимация/локальный таймер не подтверждают серверный результат.
- Базовую поставку бери из ТЗ/SRS/MoSCoW и DOC-061: не добавляй неработающие кнопки будущих функций. Backend-интеграция, FCM и модель не считаются готовыми по локальной фикстуре.

## Проверка и завершение

Подбери тесты по изменённому поведению: unit для переходов/протокола, widget для достижимости действий и состояний, fake-API integration для сценария. Для ключевых изменённых экранов апрува, ленты и mapping используй golden Dark/Light, если клиентская тестовая среда доступна. Не обновляй эталоны автоматически ради зелёного результата.

Проверь доступность по DOC-061 § 8: размеры touch targets, Semantics, порядок фокуса, большой шрифт, длинные аргументы, обе темы, reduce motion. Перечень обязательных состояний бери из § 5. Ограничивай рост ленты; время доставки/отображения измеряй по DOC-057, а не заявляй по выбору виджета.

Запусти доступные format/analyze и релевантные тесты из фактического корня Flutter-пакета. Если SDK/клиента нет, сообщи ограничение; не называй спецификацию или созданный файл проверенной сборкой. Обнови затронутые DOC-061, DOC-020, backlog, status/plan и трассировку по фактическому evidence.

Соблюдай уже согласованные этапные gates. Само использование навыка не создаёт нового требования согласовывать каждую техническую правку. Объём, обязательные требования, сроки и покупки остаются решениями владельца.
